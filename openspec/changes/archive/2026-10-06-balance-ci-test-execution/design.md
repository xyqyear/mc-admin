## Context

See `proposal.md`, `backend/docs/testing.md`, `e2e/docs/architecture.md` and `docs/release.md`. Baseline qualification 36148282102 passed 2,183 backend cases, 81 API cases and six browser journeys. Its backend matrix has 25 serial directory groups; API grouping preserves fresh-case and reusable-recipe boundaries but hashes groups without cost information.

## Goals / Non-Goals

Reduce elapsed time with four independent backend runners and three API runners, retaining sequential pytest execution per runner. Timing history influences placement only: discovery and explicit capability/selection policy determine the complete test set. Retain existing product, isolation, release and cleanup contracts.

Do not publish a release, retry failed assertions into success, disable real integration checks, or trust unrelated historical qualification artifacts.

## Decisions

1. Backend planning uses deterministic longest-cost-first assignment of whole files, with shared fixture boundaries kept together where required. Versioned baseline data documents its source and approximate log-interval measurement. Unknown files receive a positive conservative cost and are discovered automatically. Plans carry node IDs and capability requirements. Execution checks the complete inventory and selection policy before selecting a shard; the final audit verifies exact-once selection and execution outcomes independently.
2. Every backend execution uploads JUnit and precise phase timings, including failures. Coverage instrumentation stays enabled; shard data is combined once for reports. Timing artifacts are independent of inventory artifacts so audit globbing cannot accept an unrelated JSON report as a manifest.
3. API groups remain the atomic allocation unit. Versioned costs use two successful samples with queue delay removed approximately; default costs handle new scenarios. Assignment considers both total worker cost and Minecraft occupancy. Random execution order remains seed-controlled after deterministic assignment. The dispatcher admits only groups whose declared Minecraft capacity fits, while environment reservation remains the ownership authority and includes cleanup. Results distinguish queue delay from actual lifecycle phases.
4. Docker fixtures ask Docker for available host ports and discover bindings after startup. Only verified owned resources are cleaned up. Pinned tool downloads fail on HTTP errors, retry transport failures within bounds, and retain checksum verification.
5. Reusable workflows use distinct component concurrency groups. Standalone branch/PR runs cancel superseded runs; release/manual qualification contexts retain separate run identities so siblings and callers cannot cancel each other. Cross-run candidate/evidence reuse is not introduced.
6. Validate the branch with the existing manual qualification workflow and `publish=false`, reusing its candidate across API and browser jobs. Cancel only redundant runs generated by this task's branch push. Retain static, backend, API, browser and candidate gates and fail closed on missing evidence.
7. Keep the world sidebar's backup/recovery component at a stable tree position as asynchronous map status resolves. The initial real CI returned the correct interrupted history row but exposed a drawer being unmounted by the sidebar's initialized/uninitialized branches. Cover the delayed transition deterministically while preserving source/safety snapshot and rollback-byte assertions; do not mask it with locator retries or longer timeouts.
8. Treat server-reference revalidation as an owned database read: consume results and close its session before propagating cancellation, then prevent external work from starting. Isolated API validation exposed archive cancellation ending in a SQLite commit error; use a gated real SQLite regression to verify the read releases locks before terminal state writes. Preserve cleanup failures and cancellation causes; do not turn failed work into success or relax archive assertions.

## Risks / Trade-offs

- Approximate baseline costs and variable runners → retain raw precise measurements, report actual before/after, and adjust reviewed weights from successful runs.
- A single slow file limits four-way balance → preserve its fixture boundary initially; use measured evidence before finer partitioning.
- Resource-aware scheduling can deadlock or leak capacity during cancellation → race-enabled framework tests cover admission, cleanup, cancellation and failure paths.
- Hosted runner availability affects wall time → separate execution, preparation and scheduling intervals; estimates are not acceptance promises.
- Coverage and test reports can expose fixture data → upload only explicit timing, coverage and redacted diagnostic artifacts.
