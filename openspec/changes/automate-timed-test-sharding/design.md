## Context

See proposal.md, docs/ci.md, backend/docs/testing.md, e2e/docs/architecture.md, frontend-react/docs/browser-tests.md and docs/release.md. All three families restore compatible audited timing history and freeze current-inventory plans; committed costs remain positive fallbacks. API qualification currently requires 85 cases, including every Huawei scenario; ordinary PR regression requires 83 cases without cloud credentials. DNSPod and Mojang retain explicit profiles. API atomic groups share one global allocation and matrix; provider requirements supply execution metadata and credential/recovery bindings.

## Goals / Non-Goals

Preserve exact coverage, deterministic planning, resource ownership, independent runner isolation and protected cloud authorization. The budget is execution plus fixture initialization and cleanup, not installation or queueing. Application behavior, persistence, assertion retries and case deadlines are outside the change.

## Decisions

1. A shared Python history transport restores and wraps component cost payloads. Versioned envelopes identify component, execution profile, compatibility fingerprint, source run/attempt/commit/branch and costs. Restore selects the latest available audited family artifact on the branch, then trusted main; absent, expired or invalid records explicitly fall back. Fingerprints represent measurement/fixture/resource configuration, not the source commit, so history remains usable across commits. Each planner restores once and distributes the frozen snapshot and plan.
2. Plans target 300 seconds with bounded automatic shard counts and separate concurrency limits. Backend retains whole-file/shared-fixture boundaries and sequential pytest. API retains Fresh/reusable groups and globally predicts serial group/resource occupancy, including the longest-group lower bound, across all groups selected by a profile. One API matrix permits up to 16 shards and eight concurrent jobs with two workers and one Minecraft slot per runner. Provider requirements do not split allocation or impose separate concurrency limits. Browser uses explicit stable case identities, serial workers and a private owned world per shard, adding repeated world setup and cleanup to every estimate. Oversized units prefer their own shard when capacity allows; plans report indivisible work, fixed overhead or shard limits that prevent meeting the target. No deadline is reduced.
3. Component adapters normalize actual phases into reusable cost payloads only after exact coverage and success audits. Backend retains per-node phases and sums them to current files. API retains lifecycle phases and accounts for reuse setup/retirement once per group. Browser adds wrapper setup/command/cleanup measurements and audits its discovered full inventory against assigned and passed case identities. Raw failed evidence remains diagnostic but is never published as successful history.
4. API qualification uses one run-level expected catalog, immutable global allocation and job matrix. Ordinary and Huawei atomic groups may share a shard. Provider dependency metadata derives from the assigned current cases and binds required private configuration, protected dns-e2e authorization and recovery to the trusted runner; that runner may execute ordinary groups while holding its required provider credentials. A trusted qualification request independently requires all current ordinary regression and Huawei cases; a self-reported reduced catalog cannot satisfy it. Ordinary PR regression selects no cloud cases and receives no cloud credentials. The aggregate API audit validates operation observations, all expected shard/case identities and provider dependencies, candidate identity, local cleanup and exact cloud scope cleanup. Release depends on this aggregate API gate and no independent DNS gate. Explicit DNSPod/Mojang selections remain explicit and are not implicitly added.
5. Shared history is scheduling evidence only; candidate artifacts and qualification receipts continue to belong to the current run. Artifact restore is read-only, history publication is an audited artifact upload, and no automatic commits or repository writes are required. Missing history does not suppress tests.
6. Unified API placement preserves api-lifecycle-v2 individual and group cost semantics, including the reusable-group lifecycle floor and fixed cleanup/recovery overhead. The profile and compatibility fingerprint remain unchanged when only placement and matrix layout change, so previously audited costs can inform the global allocation. Historical plans and candidate receipts are not reused.

## Risks / Trade-offs

- Larger matrices repeat fixture work and encounter account queueing: keep a maximum shard count and explicit concurrency budgets, report preparation separately.
- Indivisible files/cases or fixed overhead exceed five minutes: report oversized units and preserve the soft target.
- Cloud recovery is distinct from Docker recovery: preserve EXIT and unconditional recovery, exact scope ownership validation and non-secret manifests.
- A mixed trusted shard needs provider credentials for all of its declared dependencies: bind authorization at runner scope and retain protected deployment refs; ordinary PR plans contain no such dependencies.
- Stale or incompatible costs produce poor placement: fingerprint execution context, retain positive fallback estimates and record the historical source.
- A partial matrix appears successful: audit complete current inventories, assignment identity, exact-once outcomes and cleanup before learning or qualification.

## Migration Plan

Apply the remaining unified-matrix tasks in this existing change, retaining its completed tasks and compatible api-lifecycle-v2 history. Keep committed initial costs as the cold-start fallback. Update scoped AGENTS, CI/component documentation and workflow/provider dependency contracts. Run only affected planner/matrix/credential/recovery tests and required static checks locally, then independently review the mixed-shard and untrusted-PR boundaries. Push and qualify the exact latest commit with publish=false. Wait silently with one persistent gh run watch command, without log/progress reads, updates, other work or duplicate polling until it exits; inspect the final result once. Reverting the global allocation can restore provider-separated placement without replacing history semantics, weakening cloud qualification or changing application data.
