## Context

动机和边界见 [proposal](proposal.md)。基线为 `029c6fe5`；历史证据为 2026-10-23 的 `mc-admin-cpu-report.html`，会话 `01a168c0-4ed7-7690-91e7-eab470023190`。历史百分比不是本次重新测得的性能结果。

当前健康服务器的 status 读取可串行启动四次 Compose；CPU、memory 和 I/O 接口又重复状态与身份查询。每个 CPU 请求另起一秒测量窗口。总览的“批量状态”实际是前端逐服务器请求，且与侧栏缓存不同。每次普通命令退出也会经过进程组确认，频繁枚举宿主机 `/proc`。

设计依照现有 [Runtime](../../../backend/docs/runtime.md)、[Minecraft 适配器](../../../backend/docs/minecraft.md)、[操作恢复](../../../backend/docs/operation-recovery.md)、[前端数据架构](../../../frontend-react/docs/data-architecture.md) 和 [操作刷新](../../../frontend-react/docs/operation-refresh.md)。一套部署仍只有一个后端写入者，前后端作为同一版本发布。

## Goals / Non-Goals

**Goals:**

- 昂贵采样与 HTTP 请求数量解耦，页面观察不启动 Compose 状态查询、等待 CPU 窗口或执行目录统计。
- 读适配器、后台采样、HTTP 投影、前端观察、进程收尾各自只有一个明确所有者。
- 移除重复查询和旧接口；控制抽象数量，以具体服务、纯计算函数和已有生命周期机制实现。
- 以行为回归、进程安全回归和同机对照测量证明优化。

**Non-Goals:**

- 不建立通用采集插件框架、第二套事件总线、时间序列持久化或跨标签页 leader 选举。
- 不为本次重构引入 Docker events、长连接 stats 订阅、额外部署服务或新权限。
- 不改变快照、恢复、取消、生命周期命令的完成语义；其清理与恢复保障是回归门槛。

## Decisions

### 1. 分离读取和控制，复用一个 Docker 读取适配器

| 所有者 | 职责 | 约束 |
| --- | --- | --- |
| `minecraft/docker/reader.py` | Engine 读取、容器身份匹配、结构化状态和 Java PID 发现 | 不做周期调度，不保存 UI 缓存，不执行生命周期命令 |
| `monitoring/` | 具体采样循环、差值基线、最近样本与失败状态 | Runtime 唯一实例，不拥有操作锁或任务终态 |
| `servers/queries.py` | 当前服务器身份及维护状态读模型 | 复用现有 registry、admission、task manager 和维护锁 |
| `routers/monitoring.py` | 认证、读取范围和响应组装 | 不执行 Docker、目录遍历或新的 CPU 采样 |
| `frontend features/monitoring` | 契约、HTTP、查询策略和数据选择 | 后端状态只存在 Query 缓存 |
| 已登录应用布局 | 挂载唯一监控刷新入口 | 页面组件只消费选定数据 |
| `operations/processes.py` | 已登记进程的停止确认和清理 | 不知道页面、指标和监控缓存 |

一次容器采样轮次先批量列出 Compose 容器，再按受管项目做结构化 inspect；每个匹配容器每轮最多 inspect 一次。保留项目级 created/running 与 `mc` service 健康状态的现有映射，覆盖额外 service、无 healthcheck、starting、unhealthy、stopped 和 restarting 情形；不直接解析供人阅读的 `Status` 字符串。

容器映射使用实际 Compose project、service 与已验证的配置/服务器身份；显式 Compose `name`、受管容器名、one-off 和非受管项目须有测试。不能假定 project 名等于 server ID，也不能仅用容器名前缀认领容器。复用现有配置解析，不重新实现通用 Compose 插值和配置引擎。

Java PID 通过 Engine 的进程列表定位，不能使用容器 init PID 替代。仅在初次发现、容器启动身份变化、原 PID 失效或归属不符时重新发现；平常直接校验已有 PID 的启动身份并读计数器。出现歧义时报告该指标不可用。

同步 SDK 工作在受管线程执行，显式设置连接/读取超时，串行化客户端访问并限制待提交工作。取消异步等待不等于同步调用结束；关闭必须等待真实调用完成后再关闭客户端。可以使用一个专用单线程执行器，提交前准入，避免默认线程池被阻塞请求挤占。

启动、停止、重建、Query/RCON 命令仍由既有 Compose 执行路径承担。需要权威状态的命令前置校验直接调用读适配器，在原有 lease/generation 校验中读取当前状态，不能调用监控缓存。内部重复状态 helper 合并为一次结构化读取的投影。

仅对原 CLI 做短 TTL 缓存仍保留子进程开销及多处失效策略；本方案选择移除读取链路的 CLI。完全改写 Compose 控制面超出当前问题且会扩大恢复风险。

### 2. Runtime 拥有具体采样循环，数据只保留最近一次

监控服务由 `runtime_factories.py` 构造，在恢复完成后启动。三个具体工作单元分别负责宿主机、容器/服务器快速指标和目录占用；不建设通用任务调度器。宿主机采样不等待 Docker，目录统计也不阻塞前两者。Runtime 启动不等待首个有效 CPU 样本或全部目录统计，Docker 故障只使监控降级。

初始参数集中为服务常量，并可通过测试构造注入；本次不扩充用户配置：

| 工作 | 初始周期/限制 | 原因 |
| --- | --- | --- |
| 宿主机 CPU、内存、load、文件系统容量 | 2 秒 | 本地轻量读取，独立于 Docker |
| 容器状态、Java CPU、内存、累计 I/O | 2 秒 | 相邻轮次形成 CPU 区间，所有观察者复用 |
| 每个存档目录的占用 | 完成后至少 60 秒；全局并发 1 | 保留 `du -sb` 含义，避免并行遍历争抢磁盘 |
| 前端监控刷新 | 可见且在线时 2 秒 | 全应用一个计时来源 |
| 快指标过期界限 | 距成功样本超过 6 秒 | 明确暴露采样落后 |
| 目录占用过期界限 | 距成功样本超过 120 秒 | 慢扫描时展示旧值和时间，不等待 |

每类工作在上一轮真实结束后才能开始下一轮，错过周期不补队列；慢目录公平轮转，每个服务器至多一个排队项。周期从单调时钟计算，响应展示实际墙钟采样时间。2 秒是目标节拍而非无条件延迟承诺；健康情况下从变化到页面可见通常在两个周期内，超时明确降级。

每个样本拥有 `value`、`sampled_at`、`quality`（`ready/pending/stale/unavailable`）及可选安全错误说明。过期界限在读取时按样本年龄判断，即使采样循环停止也不能永久显示 ready。采样失败立即将旧样本标为 stale；无旧样本则 unavailable。预热为 pending。确认停止后运行指标为空且说明未运行，不保留貌似当前的旧 CPU。

服务器样本以 `ServerRef` 归属；运行计数器基线再绑定 container ID、容器启动身份、Java PID 和进程启动时间。容器重启即使复用 ID，也重置基线。删除、重建及配置变化期间的旧结果在发布前重新验证身份，失败则丢弃。非运行容器、重建后的新容器和未发现 Java 的启动阶段分别处理。

读模型不写数据库，不无限保存历史。恢复旧镜像无需指标数据迁移。服务关闭先停止调度，再清理 `du` 和受管线程，最后释放依赖；不得用取消 coroutine 代替实际工作结束。遵守 Runtime 对脱离请求的 operation context 隔离。

### 3. 用计数器差值计算 CPU，保留指标含义

Java CPU 使用同一进程相邻采样的 `user + system` CPU 秒数：

```text
CPU% = (本次 CPU 秒数 - 上次 CPU 秒数)
       / (本次单调时间 - 上次单调时间) × 100
```

不除以宿主机核数，不纳入子进程时间。实际间隔随采样耗时变化，不能假设永远等于两秒。第一份计数器只建立基线；PID 变化、计数器倒退或无效区间重新预热。HTTP 不等待这个区间。

宿主机 CPU 同样用累计计数器差值，沿用 psutil 的系统 busy/total 口径：处理 idle/iowait、guest 重复计数及倒退计数，保持 0–100% 的宿主机范围。采用显式基线，避免 `cpu_percent(None)` 在线程池不同线程或新建 Process 对象上重复得到初始零值。以独立计算样例和真实负载交叉核对公式。

容器内存保留现有 `anon + file` 口径，不能在此次优化中改成 JVM heap 或 Docker CLI 的减缓存显示口径。磁盘和网络保持累计字节值及现有累计展示，不引入速率状态；实例变化时直接展示新实例的计数。已有 cgroup 和 network 解析器继续拥有原始读取，指标失败各自降级。

目录占用保留原本 `du -sb` 业务含义；文件系统 total/available 使用现有本地统计能力，保持可用空间含义，不为 `df` 单独启动进程。暂不重写目录扫描算法。

### 4. 一个 HTTP 读模型，一个前端刷新所有者

`GET /api/monitoring` 返回宿主机与受管服务器的最近样本。服务器条目携带 generation、容器启动身份的公开不透明标识及各指标的新鲜度；不公开原始 inspect、进程命令行或环境变量。无需把整个响应当作同一时间点：每个指标保留自己的采样时间。

请求中允许一次轻量服务器 registry 查询，以当前 ACTIVE 身份筛选结果，防止旧代次样本按同名拼接到新服务器。配置解析、Docker 和文件遍历均在后台。新 registry 身份尚无样本时返回 pending。后台发布前的身份核验与 HTTP 筛选共同隔离慢采样结果。

维护状态提取到 `servers/queries.py`，按当前服务器集合一次投影：恢复原因优先，其次活动 lifecycle task、删除冻结、维护 holder。直接读取已有内存所有者，避免复制状态，也避免每台服务器重复扫描全部任务。维护投影不经过两秒采样缓存，明确覆盖操作开始和结束；不能从终态事件反推活动维护。

前端新增一个具体 `monitoring` feature。`MonitoringObserver` 由已登录布局挂载一次，拥有唯一启用轮询的 Query observer；各页面使用同一 query key 的只读订阅和 `select`。禁止页面重新声明计时器或把响应复制到 Zustand/另一套逐服务器缓存。相同 key 只能合并同时在途的请求，不能消除独立 observer 的轮询计时器，这是选择唯一所有者的原因。

现有操作受理/终态刷新映射指向监控 key；立即重读会得到当前维护状态，指标仍诚实展示最近采样时间，并在下一轮更新，不在 HTTP 中强制采样。任务进度、结果与中断恢复继续使用既有共享 SSE，监控不添加第二套任务发现或事件连接。

隐藏/离线暂停周期读取，恢复可见/联网立即刷新；操作唤醒在不可观察时仅标记失效，恢复后读取。注销取消在途 HTTP 并清理会话数据，迟到响应不能进入新会话。不同浏览器标签可各有一个轻量 HTTP 轮询，但后端采样始终共享。既有快照活动发现和破坏性操作保护不改为监控轮询。

HTTP 读取失败时，界面可保留上次值，但必须显示更新失败/过期；后台仍在成功采样不能被客户端假定。只读订阅继续接收缓存变更，禁用的是主动取数，不是订阅本身；读取与失效共享唯一 key，现有取消在途旧读取的刷新规则继续生效。

删除以下被替代读取及其契约/查询键：服务器 `status`、`maintenance`、`cpu_percent`、`memory`、`iostats`、`disk-usage`，`servers/overview`，system `info`、`cpu_percent`、`disk-usage`。服务器静态列表/配置、玩家、备份容量及 health 保持独立。迁移时清点所有内部调用及 E2E，不能只改总览。

对比方案：每指标独立缓存会继续产生重复身份获取和失效规则；把指标加入已有 SSE 需要新增推送、重连和背压语义。单个轻量快照读取足以解决本轮问题，维护负担更低。

### 5. 进程清理保留一个路径，只增加有证据的快速判断

`_confirmed_exit` 保留 boot ID 校验。对于有效且大于 1 的已登记 PGID，在当前支持的同一 PID 命名空间中使用信号 0 查询进程组是否存在：

- 明确返回 ESRCH：该进程组已不存在，可以确认结束，无需枚举 `/proc`。
- 存在、EPERM 或无法得到明确结论：进入原有扫描和身份校验；错误不得解释为已经停止。
- 仅有僵尸、PGID/PID 复用、父进程先退出但组内仍有子进程：由现有详细确认路径处理，不能只看父进程 returncode。

信号 0 只作存在性检查，不执行终止。实际停止继续使用已验证身份的 pidfd，保留“冻结后枚举直到稳定”、TERM/CONT/KILL、管道排空、journal 确认及未知 writer 阻塞。无归属或命名空间条件不满足时保守处理；不新增可由调用方选择的 `skip_cleanup` 或不受管 subprocess 分支。

该改动不会消除真正需要清理的进程组扫描；收益在于正常短命令退出后通常无需全机枚举。再结合监控读路径不启动 Compose，扫描次数与被扫描规模的乘积会明显下降。保留当前 ProcessIdentity 持久化格式，历史中断记录继续可恢复。

不采用每操作 cgroup、subreaper 或删除 gate：这些方案增加权限、部署和进程语义变更，当前优化不需要承担这些成本。

### 6. 验证效果和安全，不只验证实现调用

行为覆盖包括身份/计数器重置、真实 CPU 指标含义、部分失败、Docker down、慢目录、操作开始与终态、缓存旧状态不能授权写入、注销迟到响应，以及 Runtime 半启动和关闭。

真实 Linux 进程覆盖短命令、父退出子存活、晚 fork、忽略 TERM、管道尚未关闭、组内僵尸、反复取消、权限错误和未知归属；用精确故障边界覆盖不易可靠制造的 PID/PGID 复用。断言进程确实停止、文件不再写入、journal/锁仍正确；快照恢复与地图任务取消的相关既有案例必须继续成立。

性能在隔离环境对照当前基线与改造版本，固定服务器、存档、负载和测量窗口。至少比较 1/6/20 台服务器、1/10 个观察客户端、侧栏与总览同时显示、无观察客户端和后台操作期间。记录整个 admin 容器及子进程 CPU 秒数、接口 p50/p95、事件循环延迟、Engine 调用、子进程数、`/proc` 扫描次数、线程/FD 和样本年龄。6 台场景用真实容器，其余可用受控 Engine 负载驱动数量曲线并明确标注，不能将模拟结果当线上数据。

结构性验收：稳态监控读取启动的 Compose ps/top 数为零；请求不进行一秒 CPU 等待；客户端数增加不增加采样轮数；已消失进程组退出确认不做全机扫描；快指标不等待慢目录；关闭后无泄漏。参考隔离场景以热缓存 API p95 < 200 ms、总览观察增量 CPU 较基线下降至少 50% 为优化目标，实际结果必须报告；不把这些环境相关数字做成不稳定的普通单测阈值，也不提前声称达成。

## Risks / Trade-offs

- [后台采样在无人访问时也有固定成本] → 用低成本 Engine/计数器读取、低频串行目录统计控制开销，明确测量无人访问基线；本轮不引入订阅租约系统。
- [服务器数增大仍有线性工作] → 每轮约一次容器列表加每个受管容器一次 inspect，计数器读取也是 O(N)；消除的是请求数/指标数对昂贵工作量的重复放大，不承诺 O(1)。
- [新鲜度与性能需要折中] → 显式时间/quality、当前维护投影和命令实时校验；用实测验证周期常量，超时不假装数据正常。
- [同步 SDK 取消不能中止线程] → 准入、超时与真实完成排空；关闭顺序覆盖半启动、在途超时和重复取消。
- [Compose 身份/状态语义存在细节] → 用真实 Docker 覆盖自定义 project、额外 service、health 与重建；失败时不可用，不能退回猜测或任意容器。
- [进程优化错误可能影响快照与恢复] → 独立提交和真实进程回归；仅对明确不存在加速，继续保留未知 writer 阻塞。上线资格验证不得以性能改善代替安全测试。

## Migration Plan

1. 实现 Docker 读适配器与针对性状态测试，再建立 Runtime 采样和新响应契约。命令实时校验同步迁移。
2. 迁移前端唯一观察入口及操作失效映射，迁移全部 API E2E 调用，删除分散旧接口和 helper；前后端只交付配套版本。
3. 独立实现进程确认快速路径，完成真实进程、快照/恢复相关定向回归和性能比较。
4. 更新 `backend/docs/monitoring.md`（新主题及索引）、runtime、minecraft、architecture、operation-recovery，以及前端 data-architecture、operation-refresh 和新 monitoring 主题/索引；更新 E2E 覆盖索引及受影响域文档。AGENTS 仅在新增阅读路由或边界要求时调整，不把实现细节写入指令文件。
5. 定向本地验证、必要静态检查与构建通过后提交推送，对最新 SHA 手动执行 `Qualify and Publish Application` 的 `publish=false` 资格验证。记录行为、清理审计和性能证据。

不需要数据库迁移或数据回填。回滚为整个应用镜像回退并刷新前端，内存样本重建，既有操作日志继续使用原恢复机制。本方案阶段不修改或压测线上；部署属于后续发布任务。
