# 共享监控性能实测

2026-11-01，在本机隔离部署中比较基线 `029c6fe5` 与本次实现；未访问生产环境。
主要收益来自移除监控路径上的 Compose 子进程、共享计数器采样和统一前端观察。
6 台服务器、1 个观察者时，admin 总 CPU 从 **282.14% 降至 7.65%**，监控读取
p95 从 **3239.5 ms 降至 30.8 ms**。扣除各自空闲成本后，观察增量 CPU 下降
约 **99.2%**，达到计划中下降至少 50%、热读取 p95 小于 200 ms 的目标。

## 环境和方法

- WSL2 Linux `6.18.54.1-microsoft-standard-WSL2`，20 个逻辑核，Docker 可用内存
  16,670,134,272 字节。CPU 的 100% 表示一个逻辑核。
- 基线镜像：`sha256:2445c074736508f0c51efc9239f52429a9458186a608282a9890525a46264a69`。
- 候选镜像：`sha256:801c90f4bcb3753df7fd2c48ef83034d014b93ad9f3d49f0d547f1590a5ca289`。
- 1 台和 6 台场景均为真实 Vanilla 1.21.11 容器。使用相同 flat world 配置、
  768 MiB 最大堆、视距/模拟距离 2、无玩家；两次部署分别初始化世界，并非复制
  线上存档。20 台场景单独使用受控 Engine，不当作真实游戏服务器压测。
- Go E2E runner 的 `base` recipe 拥有隔离 admin、目录和容器清理；测试服务器
  带本次 run/environment 标签，使用动态预留端口和 Docker 内建 bridge。
  实际操作仍通过公开 API 受理，并等待任务终态。
- 健康后预热 10 秒，目标采集窗口 30 秒，等待在途请求返回后计算实际时长；
  每条请求流不重叠，完成后再等待其周期。旧版依据总览+侧栏配置频率请求状态
  两路/5 秒、CPU/内存各 3 秒、维护 1 秒、目录 30 秒，以及宿主机指标；新版
  每个观察者每 2 秒读一次统一监控。双方均排除没有改变的玩家、快照容量查询。
- 用整个 admin cgroup 的 `cpu.stat` 差值计量，包含 Compose 等子进程。API
  延迟使用单调时钟；另每 200 ms 查询公开 health，作为服务响应性指标，
  **不把 health 延迟冒充事件循环延迟**。实际事件循环延迟另在受控测试记录。
- 系统调用跟踪另开诊断窗口，避免把 strace 的明显额外开销计入性能表。

复现入口（WSL，仓库根目录；run ID 必须唯一）：

```bash
/root/.cache/mc-admin/e2e/mc-admin-e2e browser \
  --backend-image mc-admin:shared-monitoring --recipe base --timeout 20m \
  --run-id perf-candidate-unique --output /root/.local/share/mc-admin-e2e \
  -- bash scripts/dev/backend.sh run python \
  ../openspec/changes/share-runtime-monitoring/benchmark.py \
  --mode candidate --seconds 30
```

基线改用 `mc-admin:mcmap-v0.9.0` 和 `--mode baseline`。需要本机 Docker、
上述 Minecraft 测试镜像和 strace。`--restart-only` 单独测量 6 台服务器下的
重启，避免先前过载影响并发操作测量。

旧版 6 台、10 个观察者已过载：请求停止后 3 秒仍有 179 个 admin cgroup
进程、536 个主进程 FD，health p95 为 5353.8 ms。因此该行不能解释为基线
正常吞吐能力，成功请求延迟也不包含失败请求。新版同场景 health p95 为
25.7 ms；三个 6 台稳态窗口排空后均为 1 个进程、34 个 FD、24 个线程。
1 台对应为 1 个进程、24 个 FD、13 个线程。观察者增加没有造成持续资源增长。

后台采样有真实空闲成本：6 台无人访问从 1.64% 增至 5.27%，约增加 3.64 个
百分点。采样仍随服务器数量增长；优化消除的是客户端数和指标数带来的昂贵
采集倍增，HTTP 认证、数据库读取、序列化和传输仍随请求数量增加。

候选 6 台的 CPU 样本年龄 p95 为 1.79 秒（1 个观察者）和 1.35 秒（10 个）。
两者都观察到 90 个不同的 `(generation, sampled_at)` 组合，即约 15 轮 ×
6 台；150 次 HTTP 读取没有变成 150 轮采样。

候选在 6 台、1 个观察者下并发真实重启，CPU 为 8.46%、p95 为 32.0 ms，
没有读取失败，操作等待真实终态。基线主测量中的重启紧接过载阶段，含前一
阶段残留工作，不用于公平比较。另在新建隔离部署中独立测量基线重启：CPU
271.05%、p95 3647.0 ms、无读取失败，操作正常完成，见
[restart-baseline.json](results/restart-baseline.json)。

## 工作量和进程收尾

strace 只统计观测到的成功 exec、Compose exec、读取 `/proc` 根目录的批次、
以及版本化 Engine GET。读取目录批次不是 Python 函数调用次数；Engine GET
也不是所有 Docker 协议请求的完整审计。跟踪窗口受在途请求拖长，不能横向
直接比较总数或跟踪阶段 CPU。

| 6 台服务器诊断 | 实际窗口（约） | 成功 exec | Compose exec | `/proc` 根目录批次 | Engine GET |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线，1 个观察者 | 26.74 s | 378 | 195 | 230 | 228 |
| 基线，10 个观察者 | 68.57 s | 992 | 451 | 810 | 556 |
| 候选，1 个观察者 | 13.01 s | 3 | 0 | 0 | 42 |
| 候选，10 个观察者 | 13.01 s | 1 | 0 | 0 | 49 |

候选 Engine GET 为 6 或 7 轮的 `(1 次 list + 6 次 inspect)`；边界轮次造成
42/49 差异。少量 exec 来自仍保留的低频目录统计。已消失进程组无需全机扫描，
存活或不确定组仍走原有归属确认和 pidfd 清理，安全回归见 [evidence.md](evidence.md)。

## 证据和限制

- [baseline.json](results/baseline.json) 和 [candidate.json](results/candidate.json)
  保留实际窗口、p50/p95、错误、采样年龄及资源读数。基线诊断时长字段的原始
  固定 13 秒元数据有误，副本依据实际测量时长加 3 秒排空修正，并注明来源；
  原始文件仍留在本机 run 目录。
- 完整本机证据：`/root/.local/share/mc-admin-e2e/perf-baseline-20261101-b/`
  与 `perf-candidate-20261101/`。两次 wrapper 均成功且清理完成。私有 fixture
  和原始系统调用日志不提交、不上传。
- 独立重启对照：`/root/.local/share/mc-admin-e2e/perf-restart-baseline-20261101/`，
  wrapper 成功，清理完成。
- 这些是同机单轮隔离对照，不是生产 SLA，也不是大存档扫描基准。窗口较短，
  周期边界、后台维护和宿主机调度会影响数字；不将时间阈值写入普通单元测试。
  慢目录和慢 Engine 的隔离、关闭排空由定向故障测试独立验证。
