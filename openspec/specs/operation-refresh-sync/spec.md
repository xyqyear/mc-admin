# operation-refresh-sync Specification

## Purpose

让已登录界面通过有界变化通知及时同步管理操作影响的业务数据，减少相同历史记录的重复传输，并在客户端断线、通知过期或服务重启后恢复界面与实际业务状态的一致性。

## Requirements

### Requirement: Authenticated incremental refresh observation

系统必须（SHALL）提供认证的操作变化增量读取，返回严格递增的变化顺序、继续读取位置、是否存在积压及运行中操作数量。变化必须（SHALL）在对应状态成功提交后可见，提供刷新所需的范围和结果类别；纯进度更新不得（SHALL NOT）造成连续刷新通知。原操作历史和任务结果读取必须（SHALL）保持可用。

#### Scenario: 未认证读取
- **WHEN** 未登录客户端读取变化
- **THEN** 请求被拒绝

#### Scenario: 旧操作结束
- **WHEN** 早先受理的操作到达成功、失败、取消、中断或跳过终态
- **THEN** 已建立读取位置的客户端可以发现该变化及其受影响范围，部分数据修改仍明确保留

#### Scenario: 没有新变化
- **WHEN** 已完成补拉的客户端再次读取，且期间没有相关变化
- **THEN** 返回空变化列表及有效继续位置，不反复返回完整历史

#### Scenario: 分页期间继续写入
- **WHEN** 客户端分页补拉期间新变化提交
- **THEN** 原积压可完整读取，新变化在后续读取中可见，不因分页跳过

### Requirement: Bounded notification retention and explicit reset

刷新通知保留必须（SHALL）具有固定条数与数据量上限，并在无法从客户端读取位置继续时明确要求重新同步。重新同步必须（SHALL）提供新的同步起点，使其后的变化仍可补拉。刷新通知丢失不得（SHALL NOT）删除真实业务结果或改变任务终态。

#### Scenario: 首次建立观察
- **WHEN** 客户端没有读取位置
- **THEN** 返回当前同步起点和重新同步要求，不要求读取全部历史

#### Scenario: 后端重启
- **WHEN** 客户端携带重启前的位置读取
- **THEN** 返回重新同步要求，原操作历史及持久化任务结果仍可读取

#### Scenario: 客户端落后于保留范围
- **WHEN** 继续位置对应的通知已被容量淘汰，或单条变化无法保留
- **THEN** 明确要求重新同步，不把缺失通知解释为没有业务变化

#### Scenario: 损坏或超前位置
- **WHEN** 客户端提交无法解析或超过当前变化范围的位置
- **THEN** 返回明确重新同步要求及当前起点

### Requirement: Session scoped cache and image synchronization

前端必须（SHALL）独立于发起页面观察操作变化，并按批合并受影响业务查询的刷新。重新同步必须（SHALL）使相关业务缓存及地图图片版本重新获取当前状态；登录会话结束后不得（SHALL NOT）沿用其读取位置。任务完成提示、错误和业务结果必须（SHALL）继续使用既有任务或功能接口。

#### Scenario: 发起页面卸载
- **WHEN** 发起页面卸载后操作产生部分修改并失败
- **THEN** 返回相关界面时可看到实际结果，无需手动刷新

#### Scenario: 丢失地图变化通知
- **WHEN** 通知重置期间地图输入已经改变但文件时间未变
- **THEN** 重新同步更新图片缓存版本，旧浏览器图片不会继续作为当前结果展示

#### Scenario: 重置时继续发生变化
- **WHEN** 前端正在重新读取业务数据，新的操作完成
- **THEN** 新变化仍可从重置提供的起点读取

#### Scenario: 首次业务读取尚未返回
- **WHEN** 重新同步或操作完成时，页面首次业务读取仍在进行
- **THEN** 获取当前业务状态，较早请求的旧响应不能覆盖刷新后的结果

#### Scenario: 时间回拨或同一操作的后续变化
- **WHEN** 需要更新地图输入的后续有效变化具有更早或相同时间戳
- **THEN** 地图图片版本仍随通知顺序更新，不依赖墙上时钟判定是否有新变化

#### Scenario: 切换登录用户
- **WHEN** 用户退出并登录另一个账号
- **THEN** 建立新观察位置，不沿用前一会话的通知或去重状态

### Requirement: Streamed operation refresh observation

前端必须（SHALL）通过共享认证事件流观察操作变化，不使用周期 HTTP 轮询。积压必须（SHALL）连续传输；成功处理刷新批次后才确认继续位置。断线或读取失败不得（SHALL NOT）推进位置或推断操作完成；重新连接必须（SHALL）使用已确认位置，并保留现有容量淘汰及重启后的明确重置语义。会话结束必须（SHALL）关闭订阅，禁止迟到批次写入新会话。

#### Scenario: 空闲后发生变化
- **WHEN** 空闲观察者连接期间新的管理操作结束
- **THEN** 观察者收到对应变化，无需等待周期 HTTP 读取

#### Scenario: 批次处理时断线
- **WHEN** 业务读取取消或刷新处理完成前连接中断
- **THEN** 未成功处理的批次不会被确认为已处理
- **AND** 重连从最近已确认位置继续，重复变化不会重复执行管理操作

#### Scenario: 隐藏或离线后恢复
- **WHEN** 浏览器在隐藏、离线或连接失败后重新建立观察
- **THEN** 从已确认位置恢复或明确重置，不丢失期间的业务变化

#### Scenario: 定时任务产生业务变化
- **WHEN** 定时任务产生现有操作变化
- **THEN** 原业务缓存刷新仍通过共享变化通知生效
- **AND** 定时任务自身的进度及日志传输行为保持原有契约
